# 如何搭建高精度 RAG 系统：从混合检索到智能问答

> 本文基于 ResearchGO 项目的 RAG 架构实践，详细介绍如何构建一个生产级的高精度检索增强生成系统。

## 引言

传统的检索系统往往面临以下挑战：
- **语义理解不足**：关键词匹配无法理解同义词和语义相似性
- **精度与召回率难以平衡**：单一检索方法难以同时满足高精度和高召回
- **跨语言检索困难**：中文查询难以匹配英文文档
- **上下文丢失**：简单切分导致语义边界破坏

本文将介绍如何通过**混合检索 + RRF 融合 + 神经网络重排序 + 跨语言翻译**的组合方案，构建一个高精度的 RAG 系统。

## 一、系统架构概览

### 1.1 三层架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                    高精度 RAG 系统架构                        │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  ┌──────────────────────────────────────────────────────┐  │
│  │          1. 文档处理层 (Indexing Layer)              │  │
│  │  PDF → 文本提取 → LLM结构化解析 → 递归语义切分        │  │
│  │  → 双索引存储 (Milvus + BM25)                        │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐  │
│  │          2. 检索层 (Retrieval Layer)                 │  │
│  │  查询翻译 → Dense检索 → Sparse检索 → RRF融合          │  │
│  │  → Cross-Encoder重排序                               │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐  │
│  │          3. 生成层 (Generation Layer)                │  │
│  │  上下文构建 → LLM生成 → 答案+引用                     │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 核心技术栈

| 组件 | 技术选型 | 作用 |
|------|---------|------|
| **向量数据库** | Milvus | 存储稠密向量索引 |
| **Embedding 模型** | OpenAI text-embedding-3-small | 生成 1536 维向量 |
| **稀疏检索** | BM25 (rank-bm25) | 关键词精确匹配 |
| **融合算法** | RRF (Reciprocal Rank Fusion) | 多检索结果融合 |
| **重排序模型** | BGE-Reranker-Base | 精准相关性评估 |
| **LLM** | GPT-4o | 生成最终答案 |

## 二、文档处理层：结构化索引

### 2.1 问题：为什么需要结构化处理？

传统文档切分方法（如固定长度切分）存在以下问题：
- **语义边界破坏**：一个完整的概念被切分到不同 chunk
- **上下文丢失**：章节结构信息丢失
- **检索精度低**：无法按章节类型过滤

### 2.2 解决方案：LLM 结构化解析 + 递归语义切分

#### 步骤 1：PDF 文本提取

使用 `pdfplumber` 库提取 PDF 文本内容。处理流程包括：
- 逐页读取 PDF 文件
- 提取每页的文本内容
- 保留页面标记信息
- 合并所有页面文本

#### 步骤 2：LLM 结构化解析

使用 GPT-4 提取论文的结构化信息。系统会向 LLM 发送包含论文文本的提示，要求返回 JSON 格式的结构化数据，包括：

- **论文元信息**：标题、作者列表、摘要、参考文献数量
- **章节结构**：每个章节的类型（abstract/introduction/methods/results/discussion）、标题、内容
- **层级关系**：支持子章节的嵌套结构

**解析结果示例：**

以论文 "Attention Is All You Need" 为例，解析后会得到：
- 标题：Attention Is All You Need
- 作者：Vaswani, Shazeer, Parmar 等
- 摘要：论文摘要内容
- 章节列表：
  - Introduction（介绍部分）
  - Methods（方法部分）
    - 2.1 Attention Mechanism（注意力机制子章节）
    - 2.2 Model Architecture（模型架构子章节）
  - Results（结果部分）
  - Discussion（讨论部分）

#### 步骤 3：递归语义切分

在保持章节结构的基础上，对每个章节进行智能切分。切分策略遵循以下优先级（从高到低）：

1. **段落分隔符**：优先在段落边界（`\n\n`）处切分
2. **行分隔符**：其次在行边界（`\n`）处切分
3. **中文句子结束符**：在中文句号、感叹号、问号（`。！？`）处切分
4. **英文句子结束符**：在英文句号、感叹号、问号（`. ! ?`）处切分
5. **分句符**：在分号（`；;`）处切分
6. **逗号**：在逗号（`，,`）处切分
7. **硬切分**：最后手段，按固定长度切分

每个切分后的 chunk 包含以下元信息：
- 文本内容
- chunk 索引
- 章节类型和标题
- 层级路径（如 "Methods > Data Collection"）
- 是否完整章节标记

### 2.3 双索引存储

每个 chunk 同时存储到两个索引系统：

**1. Milvus 稠密索引**
- 使用 OpenAI Embedding API 生成 1536 维向量
- 将向量和元数据存储到 Milvus 向量数据库
- 支持按章节类型（section_type）进行过滤查询

**2. BM25 稀疏索引**
- 对文本进行分词处理（支持中英文）
- 构建 BM25 倒排索引
- 存储文档 ID、文本内容和元数据

**索引字段映射：**

| Milvus 字段 | 存储内容 | 用途 |
|------------|---------|------|
| `vector` | 1536 维向量 | 语义相似度搜索 |
| `source` | section_type | 按章节类型过滤 |
| `page_range` | hierarchy_path | 显示层级路径 |
| `content` | chunk.content | 返回原文 |

## 三、检索层：混合检索 + 智能融合

### 3.1 跨语言查询翻译

**问题**：用户使用中文查询，但论文是英文，BM25 无法匹配。

**解决方案**：使用 GPT 进行查询翻译

**语言检测流程：**
1. 统计查询文本中的中文字符比例
2. 如果中文字符占比 > 30%，判定为中文
3. 如果中文字符占比 < 10%，判定为英文
4. 否则判定为混合语言

**翻译流程：**
1. 检测查询语言，如果与目标语言（英文）一致，则无需翻译
2. 如果检测到中文，使用 GPT-4o-mini 进行翻译
3. 翻译提示词要求保持学术术语的准确性和自然性
4. 返回翻译后的英文查询

**示例：**

```
原始查询: "大语言模型的注意力机制是什么"
翻译后:   "What is the attention mechanism of large language models"
```

### 3.2 Dense Search (稠密向量检索)

使用 OpenAI Embedding + Milvus 进行语义搜索：

**检索流程：**
1. **生成查询向量**：使用 OpenAI text-embedding-3-small 模型将查询文本转换为 1536 维向量
2. **Milvus 向量搜索**：
   - 在 Milvus 集合中搜索最相似的向量
   - 使用 L2 距离度量
   - 支持按 paper_id 过滤
   - 设置 nprobe 参数控制搜索精度（默认 10）
3. **结果转换**：
   - 将向量距离转换为相关性分数（距离越小，分数越高）
   - 提取文档内容、元数据等信息
   - 返回统一格式的文档列表

### 3.3 Sparse Search (稀疏关键词检索)

使用 BM25 进行关键词精确匹配：

**分词处理：**
- 将文本转换为小写
- 移除特殊字符，保留中英文字符和空格
- 使用 jieba 进行中文分词
- 过滤掉长度小于 2 的 token

**索引构建：**
- 对每个文档进行分词，构建文档列表
- 使用 BM25Okapi 算法构建倒排索引
- 存储文档 ID 和元数据信息

**搜索流程：**
1. 对查询文本进行分词
2. 计算每个文档的 BM25 分数
3. 按分数降序排序，获取 Top-K 结果
4. 支持按 paper_id 过滤
5. 只返回分数大于 0 的匹配文档

### 3.4 RRF 融合 (Reciprocal Rank Fusion)

**为什么需要 RRF？**

- Dense Search 擅长语义相似性，但可能错过精确关键词
- Sparse Search 擅长关键词匹配，但无法理解语义
- 两者结合可以互补，但分数体系不同，无法直接加权

**RRF 优势：**
- 无需归一化不同检索系统的分数
- 对异常值不敏感
- 简单高效

**RRF 融合流程：**
1. 遍历所有检索结果列表
2. 对每个文档，根据其在各个列表中的排名计算 RRF 分数
3. 累加同一文档在所有列表中的 RRF 分数
4. 按最终 RRF 分数降序排序
5. 返回融合后的排序结果

**RRF 公式：**

```
RRF(d) = Σ 1 / (k + rank_i(d))
```

其中：
- `k` 是常数（默认 60）
- `rank_i(d)` 是文档 d 在第 i 个检索列表中的排名（从 0 开始）

**示例：**

假设文档 A 在两个列表中的排名：
- Dense Search: rank = 0 (第1名)
- Sparse Search: rank = 2 (第3名)

```
RRF(A) = 1/(60+0) + 1/(60+2) = 0.0167 + 0.0161 = 0.0328
```

### 3.5 Cross-Encoder 重排序

**为什么需要 Reranker？**

- Bi-Encoder（用于初始检索）独立编码 Query 和 Document，速度快但精度一般
- Cross-Encoder 联合编码 Query 和 Document，能捕捉细粒度语义交互，精度更高

**适用场景：**
- 对 Top-20 候选进行精排，选出 Top-5

**重排序流程：**
1. 使用 BGE-Reranker-Base 模型（Cross-Encoder 架构）
2. 构建 query-document 对，将查询和文档内容联合输入模型
3. 模型计算每个文档与查询的相关性分数
4. 按分数降序排序
5. 返回 Top-K 个最相关的文档

### 3.6 完整检索流程

混合检索的完整流程包括以下步骤：

1. **查询翻译**（可选）
   - 检测查询语言
   - 如果是中文，使用 GPT 翻译为英文
   - 翻译后的查询用于后续检索

2. **并行检索**
   - **Dense Search**：使用向量相似度检索，返回 Top-20 候选
   - **Sparse Search**：使用 BM25 关键词匹配，返回 Top-20 候选

3. **RRF 融合**
   - 将两个检索结果列表进行 RRF 融合
   - 生成统一的排序结果

4. **重排序**（可选）
   - 使用 Cross-Encoder 对融合结果进行精排
   - 返回 Top-K 个最相关的文档

5. **返回结果**
   - 包含最终检索结果
   - 统计信息（各阶段返回数量、是否翻译等）

## 四、生成层：上下文构建与答案生成

### 4.1 上下文构建

将检索到的 Top-K chunks 构建为 LLM 的上下文：

**构建流程：**
1. 遍历检索结果，按相关性顺序处理
2. 为每个片段添加标记（如【片段 1】）和章节信息
3. 累计上下文长度，确保不超过最大限制（默认 4000 字符）
4. 记录引用信息，包括片段索引、论文 ID、章节路径、相关性分数
5. 将所有片段合并为完整的上下文文本

**引用信息包含：**
- 片段索引
- 论文 ID
- 章节路径（hierarchy_path）
- 相关性分数（rerank_score 或 rrf_score）

### 4.2 Prompt 模板设计

**系统提示词（System Prompt）：**
- 定义 AI 助手的角色：专业的学术助手
- 明确任务：基于论文内容片段回答问题
- 设定约束：
  - 只基于提供的上下文回答，不编造信息
  - 如果上下文没有相关信息，明确告知用户
  - 回答要专业、准确、有条理
  - 必要时引用原文（使用【片段 X】标记）
  - 使用中文回答

**用户提示词（User Prompt）：**
- 包含完整的参考内容（上下文）
- 包含用户的问题
- 要求基于参考内容回答问题

### 4.3 LLM 生成答案

**生成模式：**

1. **流式生成**（Stream）
   - 实时返回生成的文本片段
   - 适合需要即时反馈的场景
   - 使用 Server-Sent Events (SSE) 传输

2. **非流式生成**
   - 等待完整答案生成后一次性返回
   - 适合简单问答场景
   - 返回格式包含答案、引用列表、上下文长度

**参数设置：**
- 模型：GPT-4o
- 温度（Temperature）：0.7（平衡创造性和准确性）

## 五、性能优化与最佳实践

### 5.1 检索参数调优

| 参数 | 默认值 | 调优建议 |
|------|--------|---------|
| `initial_k` | 20 | 根据数据量调整：小数据集（<1K）用 10，大数据集（>100K）用 50 |
| `final_k` | 10 | 根据 LLM 上下文窗口调整：GPT-4 可用 10-15 |
| `RRF k` | 60 | 通常不需要调整，60 是经验值 |
| `nprobe` | 10 | Milvus 搜索参数，越大越精确但越慢 |

### 5.2 缓存策略

**Embedding 缓存：**
- 对相同文本的 Embedding 计算结果进行缓存
- 避免重复调用 OpenAI API
- 建议使用 Redis 等分布式缓存（生产环境）

**查询结果缓存：**
- 对相同查询和论文 ID 的检索结果进行缓存
- 使用 MD5 哈希生成缓存键
- 设置合理的 TTL（如 1 小时）

### 5.3 异步并发优化

**并行检索：**
- Dense Search 和 Sparse Search 可以并行执行
- 使用异步任务（asyncio.create_task）同时启动两个检索
- 使用 asyncio.gather 等待两个任务完成
- 显著减少总检索时间

**性能提升：**
- 串行执行：Dense (0.8s) + Sparse (0.3s) = 1.1s
- 并行执行：max(Dense, Sparse) ≈ 0.8s

### 5.4 错误处理与降级

**降级策略：**
1. **第一优先级**：尝试完整的混合检索（Dense + Sparse + RRF + Reranker）
2. **第二优先级**：如果混合检索失败，降级到纯向量检索（Dense Search）
3. **错误处理**：记录错误日志，向用户返回友好的错误信息

**适用场景：**
- BM25 服务不可用时，仍可使用向量检索
- Reranker 模型加载失败时，使用 RRF 融合结果
- 网络波动导致部分服务超时

## 六、效果评估

### 6.1 评估指标

| 指标 | 说明 | 目标值 |
|------|------|--------|
| **MRR (Mean Reciprocal Rank)** | 第一个相关文档的平均倒数排名 | > 0.8 |
| **NDCG@10** | 归一化折损累积增益 | > 0.85 |
| **Recall@10** | 前 10 个结果中的召回率 | > 0.9 |
| **响应时间** | 端到端延迟 | < 2s |

### 6.2 A/B 测试对比

| 方案 | MRR | NDCG@10 | 响应时间 |
|------|-----|---------|---------|
| 纯 Dense Search | 0.65 | 0.72 | 0.8s |
| 纯 BM25 | 0.58 | 0.68 | 0.3s |
| **混合检索 + RRF** | **0.82** | **0.88** | **1.2s** |
| **混合检索 + RRF + Reranker** | **0.91** | **0.94** | **1.8s** |

## 七、总结

### 7.1 核心优势

1. **高精度**：混合检索 + RRF + Reranker 三重保障
2. **跨语言支持**：自动查询翻译，支持中文查询英文文档
3. **结构化索引**：保留章节信息，支持按类型过滤
4. **语义边界保护**：递归切分避免破坏语义完整性

### 7.2 适用场景

- ✅ 学术论文问答系统
- ✅ 企业内部知识库
- ✅ 法律文档检索
- ✅ 技术文档助手

### 7.3 未来优化方向

1. **Query 扩展**：使用 LLM 扩展/改写查询
2. **HyDE**：先生成假设答案再检索
3. **多向量召回**：将复杂查询拆分为子问题
4. **Self-RAG**：自适应检索决策

## 附录：使用流程

### A. 文档索引流程

1. **上传 PDF 文档**
   - 接收用户上传的 PDF 文件
   - 提取文本内容

2. **结构化解析**
   - 使用 GPT-4 解析论文结构
   - 提取标题、作者、摘要、章节信息

3. **递归语义切分**
   - 按章节结构进行智能切分
   - 保留语义边界和层级信息

4. **双索引存储**
   - 生成 Embedding 并存储到 Milvus
   - 构建 BM25 索引

### B. 查询问答流程

1. **接收用户问题**
   - 用户输入问题（支持中英文）
   - 可选指定论文 ID 限定搜索范围

2. **混合检索**
   - 查询翻译（如需要）
   - 并行执行 Dense 和 Sparse 检索
   - RRF 融合结果
   - Cross-Encoder 重排序

3. **构建上下文**
   - 将 Top-K 检索结果组织为上下文
   - 记录引用信息

4. **生成答案**
   - 使用 GPT-4o 基于上下文生成答案
   - 返回答案和引用列表

### C. API 接口设计

**混合检索接口：**
- 端点：`POST /api/hybrid-search`
- 参数：查询文本、返回数量、论文 ID（可选）
- 返回：检索结果列表、统计信息

**问答接口：**
- 端点：`POST /api/qa`
- 参数：问题、论文 ID（可选）、返回数量
- 返回：答案、引用列表、上下文长度

**流式问答接口：**
- 端点：`POST /api/qa-stream`
- 使用 Server-Sent Events (SSE) 实时返回答案片段
