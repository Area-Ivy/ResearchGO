# ResearchGO 项目改进部分

## 1. 项目改进总览

在原有 ResearchGO 系统基础上，本阶段围绕“可用性、真实性、可维护性和智能化能力”进行了集中改进。系统不再停留在静态演示层面，而是进一步打通了论文上传、向量索引、文献检索、AI 对话、论文分析、长期记忆和前端交互等关键流程，使平台从单一功能集合逐步完善为面向科研场景的智能研究助手。

本次改进主要体现在以下几个方面：一是优化前端页面与操作流程，提高用户在论文管理、AI 对话和知识编辑中的操作效率；二是完善后端微服务接口，使论文、对话、记忆等核心数据能够被真实读取和更新；三是增强 AI 研究辅助能力，使系统能够围绕用户上传论文和长期偏好提供更连续的服务；四是改进部署与工程结构，使系统在服务器环境中具备更好的运行稳定性和扩展空间。

## 2. 前端页面与交互改进

### 2.1 页面结构优化

系统前端延续深色科技风格与侧边栏导航结构，对功能入口进行了重新梳理。原先静态 Dashboard 页面被移除，主功能聚焦于 Chat、Memory、Literature Search、Paper Library 和 Paper Review 等实际可用模块，避免展示层内容与真实数据能力脱节。

Paper Library 页面进一步增强了论文管理能力。在原有上传、下载、删除和索引状态展示的基础上，新增论文重命名功能。用户可以直接在论文列表中点击编辑按钮修改论文展示名称，系统会即时更新列表显示，并在后续下载时使用新的文件名，提升了论文整理和归档体验。

### 2.2 状态反馈优化

针对论文上传和索引过程，前端增加了更明确的状态展示，包括 uploaded、indexing、indexed 和 failed 等状态。用户可以直接看到论文是否完成向量索引，以及失败时的错误提示。对于正在索引的论文，页面通过轮询机制刷新状态，减少用户手动刷新页面的成本。

### 2.3 记忆编辑能力优化

系统新增 Memory 页面，使用户能够像 Claude Code 一样直接查看和编辑长期记忆 Markdown 文件。前端提供加载、保存、清空、行数和字节数统计等基础操作，使长期记忆从后台隐式存储变为用户可感知、可控制的知识资产。

## 3. 后端接口与数据流改进

### 3.1 论文管理接口完善

paper-storage-service 新增论文重命名接口：

```http
PATCH /api/papers/rename/{object_name}
```

该接口只修改论文的展示名称 `original_name` 和标题字段 `title`，不改变 MinIO 中的 `object_name`。这样既满足了用户修改论文名称的需求，又避免破坏下载、删除、索引和向量检索等依赖 object_name 的既有链路。

### 3.2 长期记忆存储方式改进

系统将长期语义记忆从不可见的后端存储方式，改为每个用户一份 Markdown 文件。后端新增：

```http
GET /api/memory
PUT /api/memory
DELETE /api/memory
```

所有接口均要求登录态，并基于当前用户 ID 读写对应的 Markdown 文件。服务器部署中，记忆文件通过 Docker Volume 挂载到宿主机目录，避免容器重建后数据丢失。

### 3.3 网关路由补齐

为了让前端生产环境能够通过同源路径访问新增接口，Traefik 动态路由中补充了 `/api/memory` 到 agent-service 的转发规则。Nginx 统一代理 `/api/` 到 Traefik，保证浏览器端接口路径稳定，降低前端配置复杂度。

## 4. AI 能力改进

### 4.1 面向论文的智能问答与分析

ResearchGO 支持用户上传 PDF 后进行文本解析、结构化切分和向量索引。完成索引后，用户可以基于论文内容进行语义搜索和问答。系统通过向量检索将相关论文片段提供给 AI，从而减少纯模型回答带来的幻觉风险，提高回答与用户本地论文库的相关性。

Paper Review 模块进一步面向论文理解场景，支持论文解析、结构化分析和思维导图等能力。用户不需要手动整理论文结构，系统可以辅助提取研究背景、方法、实验结果和核心结论。

### 4.2 文献检索能力改进

Literature Search 模块接入 OpenAlex 文献数据源，支持用户检索大规模学术论文，并查看标题、作者、年份、引用量、开放获取链接等信息。结合 AI 总结和对话能力，系统能够帮助用户快速完成论文初筛、主题理解和研究方向探索。

### 4.3 长期记忆辅助对话

长期记忆模块用于保存用户的稳定偏好、研究兴趣、任务背景和重要发现。AI 对话时会读取当前用户的 Markdown 记忆内容作为上下文，使回答能够更贴近用户长期需求。例如用户可以在 Memory 页面中手动写入研究方向、回答偏好或项目背景，后续对话将基于这些信息生成更连续的回复。

## 5. 工程质量与部署改进

### 5.1 微服务职责划分

系统后端按照业务能力拆分为多个服务，包括 agent-service、paper-storage-service、vector-search-service、conversation-service、literature-search-service、analysis-service 和 mindmap-service 等。各服务围绕清晰职责提供接口，便于后续独立扩展和维护。

### 5.2 数据持久化改进

论文文件存储在 MinIO 中，论文元数据存储在 MySQL 中，向量索引存储在 Milvus 中，长期记忆以 Markdown 文件挂载到宿主机目录。不同类型的数据采用不同存储方式，有助于兼顾检索效率、结构化管理和用户可编辑性。

### 5.3 服务器部署改进

系统已在服务器 Docker Compose 环境中完成部署。前端通过 Nginx 暴露 Web 服务，后端通过 Traefik 统一网关转发，多个微服务运行在同一 Docker 网络内。新增功能上线时，采用备份远端文件、上传修改文件、按服务重建容器、健康检查和接口验证的流程，降低部署风险。

## 6. 当前不足与后续改进方向

### 6.1 自动记忆提取仍需增强

当前长期记忆已经支持 Markdown 编辑，但自动从对话中提取记忆仍主要依赖大模型判断。对于一些简短但明确的用户偏好，模型可能因为重要性判断不足而没有写入。后续可以增加规则化识别机制，将“以后回答更简洁”“默认用中文”等明确偏好稳定写入长期记忆。

### 6.2 向量索引元数据同步仍可优化

论文重命名目前优先更新 paper-storage-service 中的元数据，前端展示和下载名称已经同步。但历史向量索引中的 file_name 和 title 仍可能保留上传时名称。后续可以为 vector-search-service 增加元数据更新接口，使检索结果中的名称也能在后端层面保持一致。

### 6.3 前端交互仍可继续产品化

目前 Paper Library 已具备上传、索引状态、下载、删除和重命名能力，但批量管理、标签分类、收藏、排序和筛选等功能仍有提升空间。后续可围绕科研资料管理场景进一步强化论文库的信息组织能力。

### 6.4 运维监控能力可进一步完善

系统已经具备容器化部署基础，但对各服务的运行状态、接口延迟、索引失败率和磁盘空间等指标仍需形成更系统的监控视图。后续可结合 Prometheus、Grafana 和日志聚合工具，建立面向生产运行的监控与告警机制。

## 7. 小结

本阶段改进使 ResearchGO 从静态演示型系统进一步转向真实可用的科研助手平台。系统不仅支持论文上传、索引、检索和分析，也开始具备用户可控的长期记忆和更完善的论文管理能力。通过前后端接口打通、微服务职责优化和服务器部署验证，项目整体的可用性、可维护性和扩展性均得到提升。后续工作将继续围绕自动记忆提取、论文元数据同步、论文库管理体验和运维监控能力展开，使系统更贴近真实科研工作流。
